## 四、为什么是 0 件（原因分析，按影响层级）

三个因素叠加导致 0 件。它们**不是并列关系**，而是分成"根因 / 环境放大 / 采集质量"三层；即使全部消除前两层，仅凭第 3 层（算法）也足以让真实游戏格子的识别失败。

### 4.1 根因（决定性，与运行环境无关）：dHash 在真实游戏渲染格上算法级失效

仓库作者自己在 `DeltaInventory/docs/accuracy-report.md`（2026-11-28）中披露，实测数据如下（均为一手原文）：

| 输入域 | 结果 | 说明 |
|---|---|---|
| 纯图标原图（CDN 下载 1663 张） | 5/5 正确，score 0.76~1.0；全库 1663/1663 自匹配 | 特征库与 StepHash 逐位一致 |
| 合成游戏格子（深色背景+边框+JPEG 压缩） | **5/5 错配**（汉明距离 11~18） | 特征库只含透明背景纯图标，未做"截图格子"域适配 |
| 官方 playable 模拟器**真实渲染格子** | **4 个真实格子全部错配**（纯图标库与背景域库均错，汉明距离 6~25） | 最接近真实游戏的输入域 |

原文结论（accuracy-report.md 第 58 行）：

> 当前识别能力仅在"纯图标"域成立。**真实游戏格子（含深色背景、光照渲染、文字标签、数量角标）上 dHash 全局感知哈希失效**——不是参数问题，而是算法层面的域漂移：图标周围的背景/文字像素主导了 9x8 采样，淹没了物品本身的纹理差异。中心裁剪、去背景、背景域重建库均验证无效或不稳定。

两个视频正是"真实游戏渲染格"域：深色格子背景、数量角标（+60 / 25 / 8/13）、中文标签（CINDER / M995 / DICH 训练头盔）、JPEG 压缩。这**正好落在 dHash 失效的输入域内**。因此即便在原生 ARM64 真机上、画面全屏清晰，这 0 件的结果也不会改变——这是决定性因素。

另有两个物理上限（accuracy-report.md 第 65 行）：1663 件物品只有 1400 个唯一外观，87 组共 350 件图标完全相同（最大组 16 件），dHash 无法区分同外观物品，识别只能返回组内任一物品。

### 4.2 环境放大因素（本 x86_64 容器特有）：OCR 降级、格数读不到

为让 App 在 Redroid 11 x86_64 里跑通，我对 `/system/lib64/libndk_translation.so` 做了两处二进制 patch（详见 `翻译桥Bug修复记录.md`）：

1. NOP 掉 `Arm64WriteToFpcr` 里过严的 FPCR 断言跳转——解决 ML Kit 触发的 SIGABRT；
2. NOP 掉 undefined 指令处理函数里的 `raise(SIGILL)`——让翻译器遇到未实现的 ARM64 指令时跳过而非崩溃。

第 2 处的代价：日志在整个采集期间持续打印：

```
E ndk_translation: Undefined instruction 0x5ea1b842 at 0x0000739b75bf8ac0
```

`0x5ea1b842` 是 ARM64 的 SCVTF（标量浮点转换）指令，属于 ML Kit tflite 推理的关键指令。它被跳过后，OCR 虽能加载模型（`common_util.h: Resizing Thread Pool: ocr_det_0 / ocr_segm`、`Loading mlkit-google-ocr-models/...` 均成功），但推理结果不可靠。直接证据：App 两次都显示 **"格数：未识别到格数（默认 3×3）"**，而视频画面里明明有 `口袋: 5/5`、`背包: 3/15`、`背包: 2/20` 等清晰的格数文字——OCR 应该能读到却没读到，说明处于降级状态。

格数识别失败的影响：GridOcr 拿不到网格尺寸，无法把画面正确切分成单个格子，后续 IconMatcher 就缺少可靠的 ROI（感兴趣区域）。这会让本就失效的 dHash 匹配更加无从谈起。

### 4.3 采集质量因素：横屏视频在竖屏设备里缩成一条，图标过小

- 视频原分辨率 2560×1600（横屏），设备物理屏 1080×1920（竖屏）。
- 尝试过 `wm size 1920x1080` + `user_rotation=1` 切横屏，但 Gallery 的播放画面仍只占屏幕中部一条（见 `frames/v2-landscape.png`、`frames/v1-playing.png`），黑边占据大部分屏幕。
- App 自身采集的是"长边 640 工作图"，实测日志为 `work=360x640`（见 `翻译桥Bug修复记录.md`）。在竖屏的一条横屏画面里，再缩到 360×640，单个物品图标只剩几十像素，远小于特征库生成时的图标尺寸，匹配精度进一步崩塌。

### 4.4 三因素的因果关系小结

```
采集质量(4.3)  → 图标过小、ROI 错误
       ↓
OCR 降级(4.2)  → 格数读不到 → 无法正确切格
       ↓
dHash 域漂移(4.1) → 即使切格正确，真实渲染格与纯图标库仍 4/4 全错配
       ↓
最终：0 件（已确认 0，待确认 0）
```

关键是：**4.1 是充分条件**。即使把 4.2（换原生 ARM64）和 4.3（全屏高清采集）全部解决，只要还用当前 dHash 算法对真实游戏格子识别，结果依然是 0 件——这是作者实测背书、与平台无关的结论。4.2 和 4.3 只会让"本来就不可能成功"的识别失败得更彻底，并在本次测试中额外表现为"连格数都没识别到"。

## 五、结论

**使用 DeltaInventory 软件对这两个视频的识别输出是：全部物资 0 件（空列表）。**

视频里实际可见的物资（人工目视，例如 v1 有 Mini-14、复合弓、UZI、M1911、DICH 训练头盔、突击手防弹背心、5.56×45 CINDER/M995 弹药、强效注射剂等；v2 有 MHS 战术头盔、武士防弹背心、GA 野战背包、CAT 止血带、5.56×45 弹药等）——这些是**人眼读到的，不是软件识别到的**，软件一件都没输出。

### 要让软件真正识别出物资，需要同时满足

1. **换算法（必须）**：按 accuracy-report 第 60 行建议，改用对背景不敏感的局部特征（SIFT/ORB + 词袋，或轻量 CNN 分类），替代全局 dHash；
2. **建标注集（必须）**：用真实游戏背包截图（含物品 id 标注）建立"格子→物品"标注集，训练 `item_detector.onnx`（当前是 mAP=0 的未训练骨架，不能用于识别）；
3. **原生 ARM64 环境（本测试环境所需）**：避免翻译桥 SCVTF 降级，让 OCR 正常读格数/数量；
4. **全屏高清采集（本测试条件所需）**：横屏视频在横屏设备全屏播放，图标尺寸接近特征库生成规格。

前两条是算法与数据层面的根本改造（作者本人给出的闭环条件），后两条只是消除本次 x86_64 测试环境的额外干扰。只有 1+2 完成，才谈得上"游戏内识别可用"。

## 七、边界澄清（避免误读）

- **不是"软件完全不能识别任何东西"**：在"纯图标原图"输入域，作者实测 5/5 正确、全库 1663/1663 自匹配命中。软件能识别的是透明背景的纯物品图标，不是游戏截图里的格子。
- **不是"导出结果时漏了"**：UI（已确认 0 种）、待确认页（暂无待确认物品）、数据库（`item_instances`/`recognition_events` 均为 0）三处一致，确认输出就是空。
- **人眼读到的物资 ≠ 软件识别的物资**：报告第五节列的物品名称是人工目视视频帧读出的，仅用于说明视频内容与"0 件"之间的落差，不代表软件输出。
- **本环境 OCR 降级如何影响结论**：它只加重了"格数读不到 → 无法正确切格"这一环（4.2），不改变 4.1 的充分性——即便 OCR 完全正常，当前 dHash 对真实渲染格仍是 4/4 全错配。
