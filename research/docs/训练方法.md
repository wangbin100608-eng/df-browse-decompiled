# 模型怎么训练（DeltaInventory 识别模型）

## 零、先说清楚"训练哪个模型"

APK 里有两个不同的模型位置，别混淆：

| 模型 | 输入 | 输出 | 现状 | 谁在用 |
|---|---|---|---|---|
| **分类器**（本次训练的） | 64×64 物品裁剪 | `[1,11]` 类别 logits | `train/net_real_final.pt` → 导出 `classifier_real.onnx` | 实验阶段，验证"真实域能不能识别" |
| **检测器**（APK 需要的） | 640×640 整图 | `[1,100,6]` = `[x,y,w,h,conf,cls]` | 仍是原版 `item_detector.onnx`（mAP=0） | `VisionEngine.detect` |

当前训练的是**分类器**，用来回答"真实游戏帧能不能识别"——答案是能（同源 68.4%）。要真正换进 APK，最终要训**检测器**。

---

## 一、训练数据从哪来（最关键的坑）

### 1.1 三条已实测失败的"偷懒"路线（别再走）

| 路线 | 实测结果 | 结论 |
|---|---|---|
| CDN 纯图标合成深色格子背景（1800 张） | 合成域 100%，真实帧 37.5% | 合成数据**解决不了域漂移** |
| CDN 图标模板匹配真实帧自动定位 | 分数 0.55 左右，位置全错 | 模板匹配本身也受域漂移影响 |
| 霍夫线自动切格 | 30+ 线簇、UI 边框混杂 | 无法可靠自动分格 |

**根因**：纯图标域与游戏渲染格（深色背景+光照+文字标签+数量角标）之间存在域漂移，这是仓库 accuracy-report 已披露的算法级问题。任何"用纯图标造数据、指望迁移到游戏格"的方法都失败。

### 1.2 唯一可行的数据：真实游戏帧上的人工/多模态标注

本次做法：我自己（多模态）看带 100px 网格的高清帧（2560×1600），目视读出物资名和格子坐标，生成 `train/real_labels.jsonl`：

```json
{"frame": "v1_2.5", "name": "5.56x45mm CINDER", "x0": 640, "y0": 570, "x1": 760, "y1": 700}
```

每条 = 帧名 + 物资名 + bbox。当前 19 条 / 11 类，全部生成裁剪预览图逐条校验过坐标正确。

**扩大数据的方法**：对 `train/annotate/` 下 13 张高清帧（都由原视频 ffmpeg 抽取），读带网格版本 `*_grid.png`，框出每个物资的 `(x0,y0,x1,y1)`，追加到 `real_labels.jsonl`。目标每类 ≥8 个样本。

## 二、分类器训练（已跑通，可复现）

脚本：`train/train_real_merged.py`

### 2.1 步骤

1. **读标注 + 建类别映射**：`name2id` 从标注里的 `name` 自动生成（当前 11 类）。
2. **裁剪真实物品**：按 bbox 从 2560×1600 帧裁出物品，统一缩放到 64×64。
3. **域内数据增广**（关键：只在真实域内扰动，不引入纯图标域）：
   - 亮度 ×[0.8,1.25]
   - 对比度 ×[0.8,1.2]
   - 随机中心裁剪 82%–100% 再放大回原尺寸（模拟不同格子占比）
   - 每个真实样本生成 16–24 个增广样本。
4. **网络**：3 层 CNN（Conv24 → Conv48 → Conv64 + MaxPool + FC），参数量极小（ONNX 仅 11.8 KB）。
5. **训练**：Adam(lr=1e-3, weight_decay=1e-4)，35–40 epoch，batch 32，交叉熵。
6. **验证**：同源 3 折分层交叉验证（同类样本分到不同折）+ 全量自测。

### 2.2 结果

| 验证 | 准确率 |
|---|---|
| 跨视频 v1→v2 | 30%（v2 独有类没训练样本） |
| 跨视频 v2→v1 | 55.6% |
| 同源 3 折 | **68.4%** |
| 全量自测 | 100% |

低分来自每类只有 1 个样本的类别；CINDER/M995/注射器（每类 3–4 个样本）跨视频都识别正确。

### 2.3 导出 ONNX

脚本 `train/export_onnx.py`，`torch.onnx.export(..., opset_version=13)`，产物 `classifier_real.onnx`（输入 `[1,3,64,64]`，输出 `[1,11]`），与 APK 的 ONNX Runtime 1.18 兼容。

## 三、检测器训练（换进 APK 的最终目标）

APK 的 `VisionEngine.detect` 输入输出是固定的：`[1,3,640,640] → [1,100,6]`，所以最终模型必须满足这个契约。

### 3.1 数据准备

- 标注格式：每张目标检测图里所有物资的 bbox + 类别。当前 19 条 bbox 分散在 2 张帧上，可作为种子；需扩到每帧标全所有物资。
- 增广：真实帧裁剪 + 亮度/对比度/JPEG 压缩 + mosaic（把多个物资裁剪拼到深色背包格子背景上，但**保留真实域外观**，不用 CDN 纯图标）。
- 类别：当前 11 类；最终要覆盖你清单里的全部物资。

### 3.2 模型选择

一个小型 YOLO 风格检测器（输入 640×640，网格预测 bbox+conf+cls），输出整理成 `[1,100,6]`（按 conf 取 top100）。训练用 PyTorch，导出 ONNX opset 13。

### 3.3 集成到 APK（数据到位后）

1. 替换 `app/src/main/assets/models/item_detector.onnx`；
2. `VisionEngine.detect` 输入输出格式不变 → **Kotlin 推理端零改动**；
3. 改 `ScanProcessor.processFrame`：把 `iconScanner.scan(bitmap, cols, rows, ...)` 换成 `visionEngine.detect(bitmap, itemTypes)`，用返回的 bbox 直接产出 `RawItem`，不再依赖 OCR 格数（绕过 OCR 切格）；
4. `./gradlew --offline assembleRelease`（已实测可成功），用 `delta-release.jks` 签名；
5. 跑两个视频验证，与你的清单比对。

## 五、一句话总结

用**真实游戏帧标注**（不是 CDN 合成）裁剪训练，域内增广 + 小 CNN，同源 3 折 68.4%；导出 ONNX 链路已验证。要换进 APK 需扩标注并训成 `[1,100,6]` 检测器；合成路线已实测证伪，别再走。
