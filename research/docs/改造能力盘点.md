## 2. 原生 ARM64 设备 / 模拟器 / aarch64 运行环境

**结论：当前没有可用的原生 ARM64 运行环境，在线设备与 Docker 镜像都是 x86_64。**

- `adb devices -l`（系统 `/usr/lib/android-sdk` 与 reverse-tools 两份 adb 结果相同）：
  - `127.0.0.1:5555` → `product:redroid_x86_64 model:redroid11_x86_64 device:redroid_x86_64`（transport_id:2）
  - `emulator-5554` → 同上（transport_id:1）
- 设备属性：`adb -s 127.0.0.1:5555 shell getprop ro.product.cpu.abi` = `x86_64`；`ro.build.version.release` = `11`。进程 `second_stage qemu=1 androidboot.hardware=redroid androidboot.redroid_width=1080 androidboot.redroid_height=1920 androidboot.redroid_dpi=480`，是 Redroid 11 容器化 Android，非 ARM64 真机/模拟器。
- Docker：`docker images` 仅 `redroid/redroid:11.0.0-latest`（2.98GB）与 `redroid/redroid:12.0.0_64only-latest`（2.17GB，64only 指 x86_64 only）；`docker ps -a` 显示 `redroid11` 容器运行 3 小时，端口 `0.0.0.0:5555->5555/tcp`。无 arm64/aarch64 架构镜像。
- QEMU：`command -v qemu-system-aarch64`、`qemu-aarch64`、`qemu-arm`、`qemu-system-x86_64` 全部 MISSING；但 Redroid 容器内部以 `qemu=1` 启动参数运行（是 Redroid 自身参数，不是外部 QEMU 用户态模拟器）。
- 宿主机：`uname -m` = `x86_64`。
- 证据：`adb devices -l` 输出；`getprop` 输出；`docker images`/`docker ps -a` 输出；`command -v qemu-*` 输出。

补充事实（影响 x86_64 上 OCR 的可用性）：`/root/盘点/翻译桥Bug修复记录.md` 与 `/root/盘点/视频识别结果.md` 记载，为让 ARM64-only 的 App 在 x86_64 Redroid 上运行，对 `/system/lib64/libndk_translation.so` 做了两处 NOP patch，其中一处跳过未定义 ARM64 指令 `0x5ea1b842`（SCVTF，ML Kit tflite 关键指令），导致 OCR 推理降级、读不到格数。**这不是原生 ARM64 环境**。

### 3.1 `item-features.json` 存的是原图还是特征向量？能否用于训练本地特征/CNN？

**存的是特征，不是原图。** 逐条核对 1663 条记录，字段并集固定为 `cat,h,hist,id,name,ph,price,w`：
- `ph`：无符号 64 位十进制字符串（示例 `6292630104836120`），是 `tools/build_features.py` 里 9×8 步长采样 + `(R*77+G*150+B*29)>>8` 灰度 + 相邻像素比较得到的 **dHash**（`FEATURES_README.md` 称 phash，代码实际为 dHash）。长度 8~19 位，1663 条齐全。
- `hist`：定长 16 个 float（所有条目 `len=16`），是 32×32 步长采样、亮度归一化的 4×4 颜色直方图。
- `w/h/cat/price/name`：元数据与价格/尺寸/类别；`w` 取值 1~4，`h` 取值 1~6，`cat` 分布 props 795 / acc 582 / ammo 119 / protect 98 / gun 69。
- **没有任何图片字节、base64、路径或像素数组**。

能否用于训练本地特征/CNN（事实层面）：
- 作为 CNN 训练样本：**不能直接当图像用**——只有 64bit 哈希 + 16 维直方图，空间信息已被丢弃。
- 作为传统匹配/检索特征：可，这正是它的设计用途（`IconMatcher`/`StepHash.java` 依赖它，且 `FEATURES_README.md` 要求与 Java 端逐位一致）。
- 真正原图需要按 `tools/build_features.py` 从 CDN 下载（默认缓存 `/tmp/df-icons`，当前该目录**不存在**）；`analysis/icon_examples.txt` 与 `item-database.json` 的 `iconPath` 给出 URL 模板。
- 训练“游戏截图格子→物品 id”的模型还缺标注集：`docs/accuracy-report.md` 明确闭环条件是“真实游戏背包截图（含物品 id 标注）→ 建立格子→物品标注集 → 训练/替换识别模型 → 真实域重测 mAP”，并写明当前无标注训练集、`item_detector.onnx` 是 `untrained-stub-v1-20261124`（mAP=0，confidence≈0.0067 低于 0.35 阈值，confidence 被压低所以没有有效检测）。
- 物理上限：1663 件中只有 1400 个唯一外观，87 组共 350 件图标完全相同（最大组 16 件），任何视觉模型都无法区分同外观物品。
- 证据：本地 `item-features.json` 内容解析；`tools/build_features.py` 全文；`tools/FEATURES_README.md`；`docs/accuracy-report.md`（远端 raw URL 见文首 + `/docs/accuracy-report.md`）；`app/src/main/assets/models/README.md`、`version.txt`。

## 6. 一句话事实汇总
1. Android 构建链完整且已实测 `--offline assembleRelease` 成功；JDK17 + SDK34 + NDK26.1/26.3 + CMake3.22 + build-tools34 齐备；但 Rust 工具链缺失，Rust 核心只能复用现有 `.so`。

5. `frames/` 有 6 张 1280×800 游戏帧，足以人工标注两段视频物资清单；原始 2560×1600 mp4 仍在，可补抽。
